## 1. Базовые URL

| Контур | Версия v3 | Версия v4 |
|--------|-----------|-----------|
| **Тестовый (песочница)** | `https://markirovka.sandbox.crptech.ru/api/v3/true-api` | `https://markirovka.sandbox.crptech.ru/api/v4/true-api` |
| **Промышленный** | `https://markirovka.crpt.ru/api/v3/true-api` | `https://markirovka.crpt.ru/api/v4/true-api` |

**Обязательные заголовки:**
- `Accept: */*` (для поддержки как JSON, так и ZIP/octet-stream)
- `Content-Type: application/json` (для POST/PUT запросов)
- `Authorization: Bearer <токен>` (для приватных методов)

## 2. Аутентификация

Процесс состоит из трёх шагов:

### 2.1 Получение случайной строки для подписи
**GET** `/auth/key`

**Пример запроса:**
```bash
curl -X GET "https://markirovka.sandbox.crptech.ru/api/v3/true-api/auth/key" \
  -H "accept: application/json"
```

**Ответ:**
```json
{
  "uuid": "a63ff582-b723-4da7-958b-453da27a6c62",
  "data": "GNUFBAZBMPIUUMLXNMIOGSHTGFXZMT"
}
```

### 2.2 Подписание данных УКЭП
- Полученную строку `data` необходимо подписать **УКЭП** (прикреплённая подпись, алгоритм ГОСТ Р 34.10-2012, CAdES).  
- Подпись возвращается в формате **Base64**.
- Примеры реализации см. в Приложении 2 документации (1С, React, Java).

### 2.3 Получение токена
**POST** `/auth/simpleSignIn`

**Тело запроса:**
```json
{
  "uuid": "a63ff582-b723-4da7-958b-453da27a6c62",
  "data": "<подписанные данные в base64>",
  "inn": "1234567890",         // опционально (при наличии МЧД)
  "details": "string",         // опционально
  "unitedToken": false         // true – получить UUID-токен, false – JWT (по умолчанию)
}
```

**Ответ (JWT):**
```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

**Ответ (UUID):**
```json
{
  "token": "string",
  "uuidToken": "123e4567-e89b-12d3-a456-426655440000",
  "expireDate": "2026-10-10T00:00:00.123Z"
}
```

**Срок действия токена:** до 10 часов (для JWT); для UUID – до истечения срока УКЭП или МЧД.

**Типичные ошибки:**
- `400` – отсутствие обязательных полей, неверный UUID, невалидная подпись.
- `403` – отсутствие прав у пользователя.

## 3. Ограничения и форматы

### 3.1 Количественные ограничения
- **Максимальное количество КИ в одном документе:** 30 000
- **Максимальный размер документа (тело `product_document`):** 30 МБ
- **Частота запросов:** не более 50 в секунду от одного участника
- **Максимум кодов в одном запросе `/cises/info`:** 10 000

### 3.2 Форматы данных
- Основной формат – **JSON** (RFC 7159, кодировка UTF-8).
- Поддерживаются также **CSV** (RFC 4180) и **XML** (с XSD-схемами).
- Для методов, возвращающих ZIP-файлы, необходимо указывать заголовок `Accept: */*`.

### 3.3 Экранирование
- Для URL – **RFC 3986** (например, `"` → `%22`).
- Для JSON – **RFC 8259** (например, `"` → `\"`).
- Для CSV – **RFC 4180** (вся строка КИ в двойных кавычках).
- Для XML – **W3C** (например, `<` → `&lt;`).

### 3.4 SLA по обработке документов (выборочно)
| Тип документа | Лимит КИ | Время обработки (90% / 95% / 95%) |
|---------------|----------|-----------------------------------|
| Списание (`WRITE_OFF`) | до 10 000 | до 1 ч / до 4 ч / до 24 ч |
| Ввод в оборот | до 30 000 | до 1 ч / до 4 ч / до 24 ч |
| Синхронные методы (информация по КИ) | до 10 000 | ≤ 1 мин |

## 4. Справочник типов документов

Полный список типов документов, доступных через единый метод создания.  
**Ключевые для инвентаризации и списания выделены жирным.**

| Код (type) | Описание | Формат |
|------------|----------|--------|
| `AGGREGATION_DOCUMENT` | Формирование упаковки | JSON |
| `REAGGREGATION_DOCUMENT` | Трансформация упаковки | JSON |
| `LK_RECEIPT` | Вывод из оборота | JSON |
| `LK_RECEIPT_CANCEL` | Отмена вывода из оборота | JSON |
| `LK_GTIN_RECEIPT` | Вывод из оборота (ОСУ) | JSON |
| `LK_GTIN_RECEIPT_CANCEL` | Отмена вывода (ОСУ) | JSON |
| **`WRITE_OFF`** | **Списание (общий документ)** | **JSON** |
| **`LK_KM_CANCELLATION`** | **Списание (для товаров из натурального меха)** | **JSON** |
| **`CIS_NOTICE`** | **Уведомление о состоянии кодов** | **JSON** |
| **`REPORT_REWEIGHING`** | **Отчёт о перевзвешивании** | **JSON** |
| **`CIS_INFORMATION_CHANGE`** | **Корректировка сведений о кодах** | **JSON** |
| `LP_INTRODUCE_OST` | Ввод в оборот. Остатки | JSON |
| `UNIVERSAL_TRANSFER_DOCUMENT` | УПД (для алкоголя, ветпрепаратов, пива) | XML |
| `UNIVERSAL_CORRECTION_DOCUMENT` | УКД | XML |
| ... (всего более 50 типов) | ... | ... |

## 5. Единый метод создания документов

**POST** `/lk/documents/create?pg={productGroup}`

**Параметры URL:**
- `pg` – код товарной группы (например, `milk`, `shoes`, `beer`). Обязательный.

**Тело запроса (общий случай):**
```json
{
  "document_format": "MANUAL",   // или "XML", "CSV"
  "product_document": "<base64-encoded JSON тело документа>",
  "type": "WRITE_OFF",           // код из справочника (п.4)
  "signature": "<base64 detached signature of product_document>"
}
```

**Для документов с двумя подписями (УПД):**
```json
{
  "document_format": "XML",
  "product_document": "<base64 тело продавца>",
  "type": "UNIVERSAL_TRANSFER_DOCUMENT",
  "signature": "<подпись продавца>",
  "second_product_document": "<base64 тело покупателя>",
  "second_signature": "<подпись покупателя>"
}
```

**Ответ (успех):**
```json
{
  "id": "уникальный_идентификатор_документа"
}
```

**Типичные ошибки:**
- `400` – отсутствие обязательных полей, неверный `pg`, некорректный JSON.
- `401` – отсутствует или невалидный токен.
- `403` – недостаточно прав.
- `409` – превышен лимит элементов (например, >100 партий в агрегации).
- `422` – тип документа недоступен для указанной товарной группы.

## 6. Структуры ключевых документов

Ниже приведены примеры тел для документов, которые необходимо **закодировать в Base64** и передать в поле `product_document`.

### 6.1 Уведомление о состоянии кодов (`CIS_NOTICE`)
Используется для установки состояния `LOST_INVENTORY` (не найдены при инвентаризации) или для планирования экспорта (для пива).

```json
{
  "participantInn": "7777777777",
  "actionDate": "2024-10-01",
  "action": "LOST_INVENTORY",
  "codes": [
    { "code": "010464444444444421KkKKkk" },
    { "code": "010464444444444421TtTTtt" }
  ]
}
```
**Параметры:**
- `participantInn` (string, обяз.) – ИНН участника.
- `actionDate` (string, обяз.) – дата документа (формат `yyyy-MM-dd`).
- `action` (string, обяз.) – `LOST_INVENTORY`, `SHIPPED_ABROAD` или `CANCEL_SHIPPED_ABROAD` (последние два – только для пива).
- `codes` (array, обяз.) – список кодов (макс. 30 000).
- Для `SHIPPED_ABROAD` дополнительно требуются `kpp`, `shippingDate`, `importerCountryCode`, `recipientInn`, `recipientName` и др.

### 6.2 Отчёт о перевзвешивании (`REPORT_REWEIGHING`)
Для товарной группы «Молочная продукция». Уточняет вес кодов.

```json
{
  "participantInn": "7777777777",
  "codes": [
    { "code": "0000000000000010010000000", "productWeight": 1111 },
    { "code": "1111111111111111111111111", "productWeight": 22222 }
  ]
}
```
**Параметры:**
- `participantInn` (string, обяз.) – ИНН.
- `codes` (array, обяз.) – массив объектов с полями:
  - `code` – КИ в статусе `INTRODUCED` без особого состояния.
  - `productWeight` – уточнённый вес в граммах (целое от 1 до 999999).

### 6.3 Списание (общий документ, `WRITE_OFF`)

```json
{
  "participantId": "7777777777",
  "dropoutReason": "OWN_USE_EXCISE",
  "withChild": false,
  "sntins": [
    "010461111111111121NNNNNNNNNNNNN",
    "010461111111111121KKKKKKKKKKKKK"
  ],
  "sourceDocType": "OTHER",
  "sourceDocDate": "2022-02-22",
  "sourceDocNum": "123",
  "sourceDocName": "other source document"
}
```
**Параметры:**
- `participantId` (string, обяз.) – ИНН.
- `dropoutReason` (string, обяз.) – причина списания (см. справочник причин выбытия).
- `withChild` (boolean, опц.) – списать агрегат вместе с вложениями (`true` по умолчанию, `false` доступно для табачных групп).
- `sntins` (array, обяз.) – список КИ (статус должен быть `EMITTED`, `APPLIED`, `INTRODUCED` или `APPLIED_NOT_PAID`).
- `sourceDocType`, `sourceDocDate`, `sourceDocNum` – обязательны, кроме случаев экспорта (`EAS_TRADE`/`BEYOND_EEC_EXPORT`).
- Для экспорта добавляются `destinationCountryCode`, `buyerId`, `fiasId`, `kpp`.

### 6.4 Вывод из оборота (`LK_RECEIPT`)

```json
{
  "inn": "7777777777",
  "action": "RETAIL",
  "action_date": "2024-01-01",
  "products": [
    { "cis": "010468888888888821lBEtVuGyhA0HO" }
  ],
  "document_type": "RECEIPT",
  "document_number": "12345",
  "document_date": "2024-01-01"
}
```
**Параметры:**
- `inn` (string, обяз.) – ИНН.
- `action` (string, обяз.) – причина выбытия (например, `RETAIL`, `DONATION`, `OTHER`).
- `action_date` – дата вывода.
- `products` – массив объектов с `cis` (КИ), могут быть также `product_cost`, `partial_quantity` (для частичного выбытия).
- Для экспорта – `destinationCountryCode`, `importerId`.
- Обязательные поля для отдельных причин – `document_type`, `document_number`, `document_date`, `kpp`, `fias_id` и др. (см. полную документацию).

### 6.5 Корректировка сведений о кодах (`CIS_INFORMATION_CHANGE`)

Пример для товарной группы «Молочная продукция»:
```json
{
  "participantInn": "7777777777",
  "codes": [
    {
      "code": ["010463333333333321KnKNn4", "010463333333333321Kn5KNk"],
      "vsd": "string",
      "productionDate": "2024-01-01",
      "variableExpiration": { "2": 1682121600000, "4": 1679443200000 },
      "tnved": "1234567890",
      "weight": "1500",
      "permitDocsOperation": 0,
      "permitDocs": [
        { "permitDocNumber": "123", "permitDocDate": "01.01.2023", "permitDocType": 2 }
      ],
      "emissionType": 2
    }
  ]
}
```
**Параметры:**
- `participantInn` – ИНН.
- `codes` – массив объектов, каждый содержит:
  - `code` – массив КИ (до 100 000, но объектов не более 1000).
  - Изменяемые поля (все опциональны, но должен быть хотя бы один):
    - `vsd` – идентификатор ВСД.
    - `productionDate`, `expirationDate`, `variableExpiration` – даты.
    - `tnved` – код ТН ВЭД (10 цифр).
    - `weight` – фактический вес.
    - `partNumber` – номер партии (для молочки).
    - `permitDocs` / `permitDocsOperation` – разрешительная документация.
    - `licences` / `licencesOperation` – лицензии (для воды).
    - `emissionType` – тип эмиссии (1 – произведён в РФ, 2 – ввезён).

## 7. Методы работы с кодами идентификации (КИ)

### 7.1 Получение информации о КИ по списку
**POST** `/api/v3/true-api/cises/info`  
Тело – массив КИ (до 10 000):
```json
["0104650117240408211dmfcZNcM4", "0104650117240408211dmfcZNcM5"]
```
Ответ – массив объектов с информацией о каждом КИ (статус, GTIN, дата выпуска, срок годности, `contractInn`, `contractName`, `quantityInPack` и др.).

### 7.2 Поиск КИ по фильтрам (v4)
**GET** `/api/v4/true-api/cises/search?gtin=04611111111111&status=INTRODUCED`  
Возвращает массив КИ, удовлетворяющих условиям.

### 7.3 История движения КИ
**GET** `/cises/history?cis=0104650117240408211dmfcZNcM4`  
Возвращает список событий с датами, типами операций и участниками.

## 8. Проверка участников по ИНН

**GET** `/participants?inns=1234567890&inns=0987654321` (не более 100 ИНН)

**Ответ (краткая информация, без токена или при несовпадении ИНН):**
```json
{
  "inn": "1234567890",
  "status": "Зарегистрирован",
  "productGroups": ["milk", "shoes"],
  "is_registered": true,
  "is_kfh": false
}
```
**Ответ (расширенная информация, с токеном и совпадающим ИНН):**
```json
{
  "inn": "1234567890",
  "name": "ООО \"Пример\"",
  "statusInn": "REGISTERED",
  "status": "Зарегистрирован",
  "okopf": "00001",
  "productGroups": ["milk", "shoes"],
  "chief": ["Иванов Иван Иванович"],
  "role": ["PRODUCER", "TRADE_PARTICIPANT"],
  "is_registered": true,
  "is_kfh": false
}
```

**Ошибки:**
- `404` – УОТ не найден.
- `400` – ИНН некорректен.

## 9. Пример полного цикла инвентаризации

Предполагаемый процесс с использованием True API:

1. **Аутентификация** – получение токена (п.2).
2. **Создание внутренней сессии** – в вашей БД (не в ЧЗ) сохраняем дату, склад, ответственного.
3. **Сканирование кодов** – добавление КИ в сессию (внутренняя таблица `ScannedMark`).
4. **Завершение сессии** – запуск фоновой задачи (Celery):
   - Получаем актуальную информацию по каждому КИ через `/cises/info`.
   - Сравниваем с ожидаемыми данными (например, статус должен быть `INTRODUCED`).
   - **Для отсутствующих (не найденных при пересчёте) кодов:**
     - Подаём `CIS_NOTICE` с `action: "LOST_INVENTORY"` для этих кодов (если они числятся на балансе, но не обнаружены).
   - **Для кодов с уточнённым весом (молочка):** подаём `REPORT_REWEIGHING`.
   - **Для кодов, которые нужно списать (окончательно):** подаём `WRITE_OFF` с соответствующей причиной.
5. **Получение результатов** – статус документов проверяется по их `id` (через `GET /doc/{docId}/info` – метод не описан здесь, но доступен).
6. **Корректировка данных** – при необходимости используем `CIS_INFORMATION_CHANGE` для исправления атрибутов кодов.

## 10. Примечания

- **Подпись:** Все документы требуют откреплённую подпись УКЭП (Base64) тела `product_document` **до кодирования в Base64**. Подпись должна быть без символов переноса строк.
- **Товарная группа:** Практически все методы требуют указания `pg` в URL или в теле документа. Убедитесь, что ваша организация подключила нужную группу в ЛК.
- **Тестовый контур:** Используйте песочницу для отладки. Тестовые сертификаты и демо-данные предоставляются по запросу.
- **Обработка ошибок:** В ответах на ошибки возвращается JSON с полем `error_message` (для статусов 400) или XML (для 401). Для методов, возвращающих ZIP, при ошибке также приходит JSON.
- **Обновления:** Документация актуальна на июль 2026. Следите за обновлениями в ЛК.
